# 第七章 总结与展望

## 7.1 工作总结

回想起这个项目的开发过程，从最初的需求调研到现在的系统测试收尾，前后差不多花了两个多月的业余时间。这个约拍社交平台算是我第一次完整参与的前后端分离项目，整个开发过程中踩了不少坑，也确实学到了很多东西。

在后端实现方面，Spring Boot的框架确实让开发效率提高了不少。以前写SSM项目的时候，光是配置XML文件就要花不少时间，现在用Spring Boot只需要在application.yml里写几行配置就能搞定，省下的时间可以多想想业务逻辑怎么实现。不过说实话，Spring Security这部分的配置确实有点复杂，特别是要自定义JWT验证逻辑的时候，看了不少文档才慢慢理解其中的门道。

数据库设计这块是整个项目里花时间比较多的部分。最初设计的时候比较理想化，想着把所有字段都放在一张表里查询起来方便。后来跟同学讨论的时候被提醒说这样不符合规范化原则，才又重新调整了表结构，把用户基本信息和扩展信息拆成了user和user_profile两张表。摄影师和模特虽然都是用户，但他们的业务属性差异很大，所以又分别设计了photographer和model_card来存储各自的业务数据。这轮调整之后，至少从逻辑上看清晰多了，虽然可能多了一些表关联查询，但换来的是数据一致性的保障，感觉还是值得的。

入驻审核功能的实现让我对业务流程设计有了更深的认识。以前总觉得审核就是点个"通过"按钮那么简单，真正做了才发现里面有不少弯弯绕绕。比如说，审核通过之后要把用户的角色更新，这很好理解；但审核拒绝的时候要不要通知用户、通过的时候要不要记录审核人信息以便后续追溯，这些问题都是开发过程中才慢慢想到的。后来在老师的建议下，给申请表加了auditor_id和audit_time字段，虽然多了一些开发工作量，但整个审核流程就完整多了。

前端部分用的是Vue 3加Element Plus，这套组合在写管理后台的时候确实顺手。Element Plus的组件封装得不错，很多常用的交互效果一两行代码就能实现，开发效率比原生写DOM高出不少。不过在调试的时候也遇到了一些糟心事，比如前后端分离之后本地开发环境的代理配置就让人头疼了一阵，最开始端口配置错了导致请求一直404，查了半天日志才发现是代理那边的问题。

测试阶段发现的问题给了我不少教训。最开始写代码的时候注意力都放在功能的正常流程上，异常情况考虑得不够充分。测试的时候才发现原来有那么多边界条件没处理好，比如用户快速连续点击按钮时的重复提交问题、图片上传失败时的错误提示不明确问题等等。这些问题虽然不大，但确实影响了用户体验，也让我意识到好的系统不仅要实现核心功能，还要把各种边界情况都处理好。

总的来说，这个项目让我对软件开发的全流程有了更直观的认识。从需求分析到架构设计，从编码实现到测试验证，每个环节都有它的价值。作为一个计算机专业的大学生，平时上课学的都是些零散的知识点，亲手做一个完整的项目才真正体会到把这些知识点串联起来是什么感觉。

## 7.2 系统不足与未来改进

虽然系统现在基本功能都能跑通了，但冷静下来看，还有不少地方存在明显的不足，有些是技术层面的，有些则是设计层面的。

数据库设计方面，目前的表结构虽然满足了基本需求，但索引的设计还有优化空间。特别是content表和user表之间的关联查询，在数据量大了之后可能会出现性能问题。另外，像user_profile这样的表虽然独立出来了，但里面有些字段的设计还是有点冗余，比如city字段既出现在user_profile里，又出现在photographer表里，虽然目前不会造成数据不一致，但总感觉不太干净。

审核功能的实现目前还是比较简单的版本。虽然加了审核人记录，但实际的审核流程还是比较线性的，没有引入像审核队列、审核优先级这样的高级特性。另外，目前的审核主要依赖管理员人工判断，缺少像资料完整性检查、敏感信息自动识别这样的自动化辅助手段。在实际运营中，如果申请量比较大的话，纯人工审核的效率可能会成为瓶颈。

订单系统这块的设计感觉还是偏简单了。目前的订单状态机只有"待支付、已支付定金、待拍摄、拍摄中、待支付尾款、已完成"这几个状态，但真实的约拍场景可能比这复杂得多。比如用户可能要改期、摄影师可能因为天气原因需要取消拍摄、双方可能需要对拍摄地点进行协商等等，这些情况目前都没办法很好地支持。要是想把这个系统做得更完善，订单状态机肯定要重新设计一番。

缓存策略方面目前几乎是空白的。所有请求都是直接查数据库，在用户量小的时候问题不大，但一旦数据量上来，数据库的压力会很明显。理论上像首页推荐、热门摄影师列表、标签聚合统计这些查询频率高但变化不频繁的数据，都应该放到Redis里缓存起来。这块内容之前只在课本上看过，真正要用到实际项目里还得再研究研究。

移动端适配也是个不得不面对的问题。现在的前端项目完全是按桌面端浏览器设计的，在手机上打开的话布局会乱成一团。虽然现在微信小程序和移动端H5都很常见，但目前这个项目只做了桌面端的管理后台，用户端的内容完全没有涉及。如果以后真的要用起来，移动端的支持肯定是必须考虑的问题。

消息通知系统的实现也比较基础，目前主要是通过站内消息的方式通知用户。但实际上像订单状态变更、审核结果通知这些内容，用户其实更希望能通过短信或者微信服务号推送的方式收到。这块功能要完整实现的话，涉及到和第三方服务的对接，开发工作量不小。

系统的安全性方面虽然做了一些基本的防护，但还有不少可以加强的地方。比如现在所有的接口都可以通过GET请求访问，这对于查询类接口还好，但如果是涉及数据修改的操作，GET请求就存在被攻击的风险。另外，用户密码目前只是做了哈希存储，没有实现多因素认证，在安全性要求较高的场景下可能不够用。

## 7.3 未来改进方向

基于上面分析的这些不足，我自己对系统后续的改进方向有一些初步的想法，虽然不一定能全部实现，但可以作为后续学习的方向来努力。

性能优化肯定是首先要考虑的事情。打算引入Redis作为缓存层，把热点数据加载到内存里，减少数据库的查询压力。图片资源的加载也需要优化，准备试试CDN分发加图片压缩的方案，看看能不能把首页加载速度再往上提一提。数据库层面的话，可能需要重新评估一下索引的设计，必要时可以考虑做读写分离或者分库分表。

智能化审核是我觉得很有意思的一个方向。如果以后申请量上来了，纯人工审核可能忙不过来。可以考虑引入图像识别技术来自动检查用户上传的证件照是否符合要求，或者用NLP技术来检测简介文本中是否包含敏感词。这样既能提高审核效率，又能保证审核标准的一致性。

订单流程的完善也是必须要做的事情。我设想过可以引入状态机来管理订单的生命周期，把改期、取消、退款等操作都纳入到统一的状态流转中。同时还要加入更完善的冲突检测机制，避免出现时间地点资源冲突的问题。也许还可以考虑接入第三方日历API，让用户能够更方便地把预约时间同步到自己的日历里。

移动端适配方面，小程序可能是性价比最高的选择。微信小程序的开发框架和Vue比较相似，有Vue基础的话上手应该不会太难。而且小程序自带的微信登录、支付等功能也能省去不少开发工作量。当然，如果想要更好的跨平台体验，也可以考虑用uniapp这样的框架，一套代码同时打包成小程序和H5。

消息通知体系的建设也值得投入。站内消息作为基础的通知渠道可以保留，但同时可以考虑接入微信公众号的模板消息，这样用户不用打开APP也能收到订单状态变更的通知。对于高优先级的通知，比如支付成功、审核结果等，还可以考虑短信兜底，确保用户一定能收到。

数据分析和可视化是运营人员比不可少的功能。目前管理后台只有简单的数据统计报表，如果以后要做精准运营、用户画像分析这些高级功能，还需要建设完整的数据仓库。可以考虑引入ECharts来做数据可视化，把用户增长、内容传播、交易转化这些核心指标做成实时更新的数据大屏。

微服务化改造是中远期的目标。现在整个后端还是一个单体应用，虽然开发的时候方便，但如果系统变得庞大之后，维护成本会越来越高。以后可以考虑按业务领域拆分成用户服务、订单服务、内容服务、支付服务等独立的微服务，通过API网关来统一对外提供服务。当然，这需要更多的服务器资源和更复杂的运维体系，目前先当作一个学习目标来规划。

回顾整个项目的开发过程，虽然遇到了不少困难和挑战，但整体来说还是一个收获满满的过程。从最初对前后端分离架构的模糊理解，到现在能够独立搭建一套完整的Web应用，这个进步是实实在在的。当然，现在这个系统还很不完善，很多地方都有改进的空间，但我相信只要持续学习和实践，系统会变得越来越好的。
