# 第六章 系统测试

## 6.1 测试环境

### 6.1.1 硬件环境

本系统的开发和测试过程中，使用了以下硬件配置：

开发工作站采用了主流的个人计算机配置，CPU为Intel Core i7第12代处理器，内存为32GB DDR4 3200MHz，硬盘为1TB NVMe固态硬盘。这样的配置能够保证前后端项目的同时运行，以及数据库的流畅操作。管理后台的测试服务器则部署在另一台开发机上，配置相对较低但足以支撑日常的调试和功能验证工作。

网络环境方面，测试期间主要使用本地局域网环境，服务器之间通过千兆网卡进行通信。前端开发服务器监听在3000端口，后端服务分别运行在8081和8086端口，其中8081端口承载主业务系统的API服务，8086端口则负责管理后台的相关功能。

### 6.1.2 软件环境

软件环境的搭建是确保系统正常运行的基础。本系统采用的是典型的前后端分离架构，因此需要分别配置前端和后端的运行环境。

后端环境基于Java技术栈，采用Spring Boot 2.7.15作为核心框架，使用Maven进行项目构建和依赖管理。JDK版本为17，这是目前Spring Boot 2.7.x系列推荐的LTS版本。数据库选用了MySQL 8.0，该版本在性能和安全方面都有较好的表现，同时也完全兼容系统所使用的的InnoDB存储引擎和相关SQL语法。

前端环境的搭建则依赖于Node.js和Vite构建工具。Node.js版本选择了v18 LTS版本，这个版本在稳定性和新特性支持之间取得了较好的平衡。Vite作为新一代的前端构建工具，在开发环境下能够提供极快的热更新速度，大幅提升了开发体验。前端UI组件库采用了Element Plus，这是Element UI针对Vue 3的全新升级版本，提供了更加现代化的组件外观和更好的TypeScript支持。

在测试工具的选择上，后端接口测试主要使用Postman这款专业的API调试工具，它能够方便地构建各种HTTP请求，并支持环境变量、集合管理等功能。前端调试则主要依赖浏览器开发者工具，特别是Chrome DevTools中的Network面板和Console面板，能够清晰地看到网络请求的详情和运行时的错误信息。

### 6.1.3 测试数据准备

为了全面测试系统的各项功能，测试前需要准备充足的测试数据。测试数据主要分为三个部分：用户数据、内容数据和订单数据。

用户数据的准备重点关注不同角色用户的覆盖。系统中设计了普通用户、摄影师、模特三种核心角色，测试时需要为每种角色创建足够数量的测试账号。摄影师用户还需要关联其个人资料信息，包括简介、擅长风格、服务价格等。模特用户则需要维护其身高体重、可预约时间、收费标准等专属信息。

内容数据的准备主要针对作品展示和需求发布两种类型。作品内容需要关联摄影师用户，并打上相应的风格标签，还要准备封面图片URL。为了测试标签筛选功能，标签的种类需要足够丰富，涵盖人像、风光、纪实、创意等主要摄影风格分类。需求内容则需要关联发布用户，并设置期望的风格类型、预算区间等筛选条件。

订单数据的准备需要覆盖订单的完整生命周期。从下单开始，经过支付定金、确认拍摄时间、实际拍摄、支付尾款到最终完成评价，每个状态转换都需要有对应的测试订单。此外还需要准备一些异常状态的订单数据，如用户申请退款的订单、摄影师取消的订单等，用于测试订单状态的异常流转处理。

## 6.2 测试方法

### 6.2.1 黑盒功能测试

黑盒测试是本项目采用的主要测试方法，这种方法将系统视为一个黑箱，测试人员不需要了解系统内部的实现细节，只关注输入与输出的对应关系。在本项目的测试实践中，黑盒测试主要应用于功能验证和业务逻辑验证两个层面。

功能验证层面，测试人员按照预先编写的测试用例，逐项检查系统功能是否符合需求规格说明书的描述。例如，在测试用户注册功能时，需要验证手机号格式校验是否生效、验证码发送间隔限制是否正确、密码强度要求是否满足等。这些测试点的设计来源于需求文档中的功能描述，但测试过程中并不依赖代码实现的具体方式。

业务逻辑验证层面，则需要站在用户实际操作的角度，设计更加复杂的测试场景。以预约摄影师为例，实际操作涉及搜索摄影师、查看作品集、选择套餐、填写预约信息、支付定金等多个步骤，测试时需要模拟完整的用户操作流程，验证每个步骤的数据流转是否正确，最终的订单状态和各方消息通知是否符合预期。

黑盒测试的优势在于它能够从用户的视角发现问题，特别是一些业务流程上的缺陷。但由于测试人员看不到代码实现，有时难以精确定位问题发生的根本原因，这就需要配合白盒测试进行进一步的分析。

### 6.2.2 白盒接口测试

白盒测试则需要测试人员具备一定的代码阅读能力，能够理解系统内部的实现逻辑。在本项目中，白盒测试主要应用于后端API接口的验证，确保每个接口的行为与预期完全一致。

接口测试的核心工具是Postman，通过构造各种参数组合来验证接口的边界条件处理能力。以用户列表查询接口为例，测试时需要考虑以下几种情况：正常参数下的分页查询是否返回正确的数据结构；不带任何参数时是否返回默认分页结果；传入不存在的角色值时接口如何响应；传入超出范围的页码时是否会返回空结果等。这些测试场景的设计，既包含了正常情况的验证，也包含了对异常情况的防御性测试。

对于涉及数据库操作的接口，还需要验证SQL语句的正确性。比如在更新用户状态时，需要确认更新的是目标用户而不是其他用户；在删除数据时，需要确认级联删除的逻辑是否符合业务需求。这些验证往往需要直接查看数据库中的数据变化，而不仅仅依赖接口返回的结果。

### 6.2.3 集成测试

集成测试旨在验证不同模块之间的协作是否顺畅。在本项目中，由于采用了前后端分离的架构，集成测试的重点主要集中在前后端联调阶段和跨系统调用两个方面。

前后端联调测试是日常开发中最频繁进行的集成测试形式。前端通过Vite配置的代理功能，将开发环境中的请求转发到后端服务，测试过程中需要验证数据请求是否成功、返回的数据结构是否与前端预期一致、错误处理是否合理等。由于前后端开发者可能对接口文档的理解存在偏差，联调测试常常能够发现一些在单独测试阶段难以发现的问题。

跨系统调用的测试主要涉及与第三方服务的交互。本系统中使用了腾讯云的短信服务发送验证码，虽然在正常情况下这些第三方服务是可靠的，但测试时仍需要验证当第三方服务出现异常时系统的容错能力。比如短信服务响应超时时，系统是否会给出明确的错误提示；验证码缓存失效后的重试机制是否正常工作等。

### 6.2.4 压力测试

压力测试的目的是评估系统在高并发场景下的性能表现。虽然本系统目前的用户规模还不需要考虑超大规模并发的情况，但在开发过程中仍需要了解系统的性能瓶颈所在。

压力测试主要使用Apache JMeter工具，模拟多个用户同时发起请求的场景。测试内容包括：多个用户同时登录时系统的响应时间变化；大量用户同时访问首页时图片加载的性能表现；搜索功能在数据量较大时的响应速度等。通过这些测试，可以发现在日常功能测试中难以暴露的性能问题，为后续的优化工作提供方向。

在实际测试中发现，图片加载是影响系统响应速度的主要因素。由于作品展示类内容需要加载多张高清图片，当前端的图片请求过于密集时，会导致页面渲染变慢。针对这一问题，在后续优化中考虑引入图片懒加载机制，并使用CDN加速图片资源的分发。

## 6.4 测试结果分析

### 6.4.1 功能测试结果概述

本次系统测试共计执行测试用例87个，涵盖了用户管理、审核流程、内容发布、交易下单、评价反馈等核心业务模块。经过多轮测试和修复，最终有83个用例完全通过，通过率达到95.4%。

未通过的4个用例主要集中在以下两个方面：首先是图片上传功能在某些浏览器环境下存在兼容性问题，Safari浏览器在上传HEIC格式图片时会转换失败；其次是退款流程中的状态机转换存在边界条件遗漏，当用户在支付完成后立即申请退款时，系统的幂等性处理不够完善。

针对测试发现的问题，开发团队已经制定了修复计划并逐步实施。对于浏览器兼容性问题，计划在后续版本中引入更加通用的图片处理库来解决HEIC格式的转换问题。对于状态机的问题，则需要细化退款流程的状态定义，增加更多的边界条件判断，确保每个状态转换都是明确和可追溯的。

### 6.4.2 接口测试结果分析

后端API接口的测试覆盖了所有对外暴露的RESTful接口，共计测试接口数量为56个。接口测试的重点关注两个方面：返回数据结构的正确性和业务逻辑的处理完整性。

在数据结构正确性方面，绝大多数接口都能够按照预先定义的JSON Schema返回正确的数据格式。发现的少数问题主要集中在时间格式的处理上，由于数据库中存储的时间是UTC时间，某些接口在返回时没有进行时区转换，导致前端显示的时间与实际时间存在偏差。这一问题在后续的优化中已经统一在网关层进行时区转换处理。

在业务逻辑处理方面，接口测试发现了几个值得关注的问题。其中较为典型的是摄影师预约时间冲突检测的问题：当多个用户几乎同时对同一个摄影师的同一个时间段提交预约时，系统没有正确处理并发冲突，导致出现了同一个时间段被多个订单占用的异常情况。这一问题的根本原因是预约时间可用性检查和订单创建两个操作没有实现原子性，在高并发场景下存在竞态条件。针对这一问题，后续优化中采用了数据库事务加锁的方案，确保了检查和创建操作的原子性。

### 6.4.3 性能测试结果分析

压力测试模拟了系统在高并发场景下的运行状态，重点关注响应时间和系统资源的消耗情况。测试设置了50、100、200三个并发级别，分别对应轻度、中度和重度负载场景。

在轻度负载场景下（50并发），系统的各项性能指标表现良好。首页的平均响应时间为320毫秒，95%分位响应时间为580毫秒，能够满足用户日常使用的需求。CPU平均使用率为35%，内存使用稳定在2.1GB左右。

在中度负载场景下（100并发），系统性能出现了一定程度的下降。首页平均响应时间上升至680毫秒，95%分位响应时间达到1.2秒，部分用户已经能够感知到页面的延迟。CPU使用率上升至65%，内存使用达到2.8GB，此时数据库连接池已经接近饱和状态。

在重度负载场景下（200并发），系统性能下降明显。首页平均响应时间超过2秒，95%分位响应时间达到5秒以上，已经严重影响了用户体验。此时CPU使用率持续处于90%以上的高位，内存使用也逼近了3.5GB的上限。从监控数据来看，数据库查询和图片加载是主要的性能瓶颈所在。

基于性能测试的结果，建议在生产环境中配置至少4核CPU和8GB内存，并考虑引入Redis缓存和CDN加速来改善系统的整体性能表现。同时，图片懒加载和分页优化也应该作为后续迭代的重点工作来推进。

### 6.4.4 安全测试结果分析

安全测试是系统测试中不可忽视的重要环节。本次安全测试主要关注身份认证、权限控制、数据传输三个方面的安全性。

在身份认证方面，测试验证了JWT Token的有效性验证机制。测试结果表明，系统能够正确识别过期的Token并拒绝访问，恶意构造的Token也无法通过签名验证。在暴力破解防护方面，系统在连续5次登录失败后会触发账号锁定机制，锁定时间内的所有登录尝试都会被直接拒绝。

在权限控制方面，通过测试发现了管理后台存在一处越权漏洞：普通管理员理论上可以访问并修改其他管理员的账户信息。这一问题的风险等级被评定为中等，因为在实际使用场景中，普通管理员通常不会故意尝试访问管理员账户，但为了确保系统的安全性，仍然需要修复。修复方案是在后端增加管理员角色的层级验证，确保只有超级管理员才有权限管理其他管理员账户。

在数据传输方面，全站启用了HTTPS加密传输，测试过程中使用抓包工具验证了敏感数据在网络传输过程中确实已被加密处理。但测试也发现部分接口的请求参数中包含了用户ID等敏感信息，虽然这些信息在HTTPS的保护下不会被第三方窃取，但从安全最佳实践的角度来看，仍建议对这类信息进行脱敏处理后再出现在日志和监控系统中。
